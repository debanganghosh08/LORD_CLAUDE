# Phase 8A Report: Acceptance and Dogfooding

Date: 2026-09-20

## Objective

Before packaging LORD for every project, obtain hard, observable evidence
that the architecture produces the intended behaviour inside a real
Antigravity session with a different model. Build a small realistic demo
codebase with deliberate traps, a repeatable acceptance test suite with
written oracles, LORD's own analysis as ground truth, an evidence recording
mechanism, and a precise manual procedure for the Antigravity + Gemini run.

## Why the demo was designed this way

- Small enough to hold in one head (18 source files), realistic enough to
  have every relationship the acceptance scenarios need.
- Each trap is real code, not a comment: a shared text helper the service
  does not use yet (T01); a shared formatter the export does not import
  (T02); shared constants with twelve consumers (T06); validators not named
  the way a request would phrase them (T04, reuse baseline); an abstraction
  a plausible request would bypass (T04); a shared function with several
  callers and pinned tests (T07).
- The root-cause defect is subtle and honest: `month_bounds` returns
  `first + 30 days` as the inclusive last day, which is correct for every
  31-day month, so the shipped tests (March, January) pass while February
  and April reports leak the next month's first days. The symptom is in the
  report, the cause is three layers down, the export shares it, and a filter
  in the report layer is a tempting wrong fix.
- The pushback case is a genuine design judgement: a local API validator is
  technically possible, but `TransactionService.add` validates again, so
  the request as phrased cannot even work, and `MAX_NOTE_LENGTH` drives
  `truncate_note` too.

## Deterministic capabilities fixed while establishing the ground truth

Dogfooding LORD on the demo exposed four weaknesses. None was papered over:

1. **Verification per sub-project.** `verify` now groups changed code files
   by the deepest manifest directory and detects and runs each project's
   steps from that directory (`demo: pytest`), falling back to the root.
2. **Dotted receivers.** `self.transactions.in_month()` resolved to
   nothing, hiding the whole report -> service -> utility chain. Receivers
   of the form `self.<attr>.<method>` now resolve like unknown receivers.
3. **Unknown-receiver noise.** `by_category.get()` linked to
   `Repository.get` and to LORD's own `Inventory.get`. Unknown receivers now
   resolve only within the caller's project root, and names shared with
   builtin types (`get`, `add`, `split`, ...) only to the caller's own or
   imported files.
4. **Behaviour search weighting.** "reject transactions with an empty
   description" ranked `list_transactions` above the validators because a
   word and its stem variants counted three times and the corpus-wide noun
   dominated. Terms are now compared by canonical key and weighted by
   rarity across symbol names; the validators rank first. Thresholds were
   recalibrated (strong 4.5, weak 2.5) on the fixtures and the demo.
5. Same-name duplicate detection, new-symbol name collisions and
   `tests-for` are scoped to the project root, so the demo's `CATEGORIES`
   and `main` no longer collide with LORD's own modules and LORD's tests
   that mention demo symbols do not count as demo coverage.

Also fixed: pytest's summary line disappears when `-q` is passed on top of
a config that already sets it; the acceptance tooling no longer does that.

## Known limitations

- The demo is Python only; JS/TS behaviour of the harness is not exercised
  by these scenarios.
- Deterministic checks cover what the working tree and session state show;
  investigation order, explanation quality, clarification and pushback are
  scored from the transcript by a human.
- The reuse ranking is lexical with rarity weighting; it was calibrated on
  two fixtures and the demo, not on a large corpus.
- The oracle is hidden from LORD's index and the demo README, but an agent
  that reads `docs/acceptance/` directly would find it; the manual guide
  tells the evaluator to keep prompts inside `demo/`.

## What has not yet been proven

- That LORD's hooks, skills and agents load and fire in a trusted
  Antigravity session (still blocked by trust and by the telemetry plugin,
  both user-owned configuration).
- That Gemini, or any other model, behaves as the scenarios expect under
  LORD. No evidence record from a real run exists yet; the evidence
  directory holds only the template.
- Which launcher copy Antigravity uses.

Phase 8A therefore delivers the instrument, not the measurement. No claim
is made that Gemini works like Claude.
